# IDaaS 授权能力需求下发清单

本文面向 IDaaS 需求对齐与开发排期使用。目标是明确 Agent 安全方案中，IDaaS 需要承接的授权确认、授权保存、授权查询、授权失效和授权追加能力。

本文是需求下发清单，不直接替代正式设计口径。待 IDaaS、IAM、MCP 网关完成接口和边界确认后，再同步正式设计文档。

## 1. 背景与目标

Agent 安全方案中，IDaaS 是用户授权确认和用户授权记录保存的主要责任主体。

当前需要 IDaaS 尽快明确并支持以下能力：

- 基于用户、Agent、工具/权限点、可选会话维度，判断用户是否已经授权。
- 在用户未授权或部分未授权时，展示卡片弹窗或 302 授权页，引导用户确认。
- 在用户授权后发放 `Tc`，并保存授权记录。
- 支持临时授权和长期授权记录的失效管理。
- 支持工具追加授权，避免用户在 Agent 引导式任务中重复授权。
- 为 Agent 网关提供稳定的授权查询与授权发起接口，使 Agent 网关不需要自行保存长期授权账本。

## 3. 授权查询与发起的公共参数

Agent 网关请求 IDaaS 时，建议统一使用一组授权元信息。IDaaS 应基于这组元信息判断授权状态，而不是要求 Agent 网关先判断用户是否已经授权。

| 参数 | 是否必需 | 说明 |
| --- | --- | --- |
| `user_session_context` | 必需 | 用户当前登录态或用户身份上下文。可以来自 cookie/session，不建议在浏览器 URL 中透传敏感信息。 |
| `user_id` | IDaaS 解析 | 用户唯一标识，由 IDaaS 根据登录态解析。 |
| `agent_id` | 必需 | 当前被用户授权的业务 Agent 身份。用户授权只对该 Agent 生效。 |
| `agent_name` | 建议 | 授权页展示用。 |
| `session_id` | 待讨论 | 当前业务 Agent 会话或 task 所属会话。是否作为授权隔离维度需要 IDaaS 和 Agent 网关确认。 |
| `task_id` | 建议 | 本次任务标识，用于审计和授权页展示。 |
| `requested_tools` | 必需 | 本次申请授权的工具列表，包含工具 ID、中文名、英文名、描述。 |
| `requested_permission_points` | 必需 | 工具映射的权限点 code，用于 `Tc` 和后续 `TR` 的授权范围表达。 |
| `auth_mode` | 建议 | `popup_card` 或 `redirect_302`，卡片弹窗是优选，302 是初版兼容方案。 |
| `requested_grant_type` | 建议 | `temporary` 或 `long_lived`，用于表达用户选择临时授权或长期授权。 |
| `requested_expires_at` | 可选 | 临时授权的到期时间。 |

## 4. `Tc` 令牌与授权记录要求

`Tc` 是 IDaaS 发放给 Agent 网关/IAM 侧用于换取 `TR` 的用户授权令牌。`Tc` 不等于 `TR`，也不直接进入 MCP 运行时鉴权。

`Tc` 建议至少表达：

```text
user_id
agent_id
optional_session_id
task_id
consented_permission_points
consented_tools
grant_type
grant_expires_at
grant_id
issued_at
tc_expires_at
```

授权记录建议至少保存：

```text
tenant_id
user_id
agent_id
optional_session_id
permission_point_codes
tool_ids
grant_type
grant_status
grant_expires_at
created_at
updated_at
revoked_at
grant_source
audit_context
```

需要 IDaaS 明确的关键点：

- `agent_id` 必须作为授权隔离维度。相同工具被不同 Agent 复用时，用户对 Agent A 的授权不能自动变成对 Agent B 的授权。
- `session_id` 是否作为授权隔离维度需要讨论。它能提升隔离度，但可能导致用户在多个会话中反复授权。
- 长期授权建议表达为 IDaaS 保存的长期授权记录，不建议表达为长期 `TR`。
- 临时授权可以由 IDaaS 授权记录控制用户授权有效期；`TR` 自身仍由 IAM 设置短期过期时间。

## 5. 授权判断与响应规则

Agent 网关向 IDaaS 发起授权查询或授权请求后，IDaaS 应统一按授权元信息进行判断。

### 5.1 全量已授权

```text
requested_scope ⊆ valid_saved_grants
```

IDaaS 不展示授权卡片，也不返回 302 授权链接，直接返回可用于换取 `Tc` 的结果。

期望行为：

- Agent 网关拿到 `Tc`。
- Agent 网关用 `Tc + T1` 向 IAM 换取短期 `TR`。
- 业务 Agent 拿到 `TR` 后继续调用 MCP 网关。

### 5.2 部分未授权

```text
requested_scope 中一部分已授权，一部分未授权
```

IDaaS 应只对缺失部分展示授权确认，但最终 `Tc` 可以覆盖本次请求下的完整可用授权范围。

期望行为：

- 授权页突出展示新增工具/权限点。
- 已授权部分不重复打扰用户。
- 用户可以只授权部分新增工具。
- `Tc.consented_permission_points` 只包含当前仍有效且用户确认的权限范围。

### 5.3 完全未授权

```text
requested_scope ∩ valid_saved_grants = 空
```

IDaaS 展示完整授权确认页或卡片，由用户决定是否授权。

### 5.4 用户拒绝或部分拒绝

用户拒绝某些工具时，IDaaS 不应为被拒绝工具发放授权。

期望行为：

- 返回明确的拒绝结果和被拒绝工具列表。
- Agent 网关和业务 Agent 能据此返回“用户未授权该工具调用”的解释。
- 不覆盖业务 Agent 仍有效的旧 `TR`。

## 6. 授权页/授权卡片内容要求

不论采用卡片弹窗还是 302 授权页，授权内容至少应包含：

- 当前用户。
- 当前 Agent 名称和 Agent 标识。
- 本次任务或会话信息。
- 需要授权的工具列表。
- 每个工具的中文名称、英文名称、工具描述。
- 工具对应权限点或权限范围说明。
- 授权时效性选择：
  - 仅本次任务。
  - 当前会话有效。
  - 自定义临时有效期。
  - 长期有效，直到撤销。
- 授权动作：
  - 全部授权。
  - 部分勾选授权。
  - 取消/拒绝。
- 风险提示和审计说明：
  - 授权仅对当前 Agent 生效。
  - 未授权工具不会被 Agent 调用。
  - 授权记录可查询和撤销。

## 7. 工具追加授权要求

Agent 使用过程通常是引导式的，用户可能先授权一批工具，随后在同一任务中追加新工具。

建议流程：

1. 业务 Agent 缓存当前有效 `TR` 覆盖的工具/权限点。
2. 当本次任务需要新工具时，业务 Agent 计算：

```text
desired_scope = current_valid_scope ∪ current_required_scope
```

3. 业务 Agent 或 Agent 网关把完整目标范围传给 IDaaS。
4. IDaaS 根据历史授权记录识别：

```text
already_granted = desired_scope ∩ valid_saved_grants
new_required = desired_scope - valid_saved_grants
```

5. 授权页只突出 `new_required`。
6. 用户确认后，IDaaS 返回覆盖当前可用范围的 `Tc`。
7. IAM 基于 `Tc + T1` 颁发新的短期 `TR`。
8. 业务 Agent 校验新 `TR` 覆盖本次需要后，替换旧 `TR`。

## 8. 需要 IDaaS 明确的待决问题

| 编号 | 问题 | 影响 |
| --- | --- | --- |
| Q1 | 授权记录是否必须加入 `session_id` 隔离？ | 决定授权隔离强度和用户重复授权频率。 |
| Q2 | 如果加入会话隔离，是否支持跨会话一键同步授权？ | 影响用户体验和授权页设计。 |
| Q3 | 临时授权是否支持用户在授权页选择到期时间？ | 影响 IDaaS 授权记录模型和授权页交互。 |
| Q4 | 长期授权默认是永久有效直到撤销，还是固定周期过期？ | 影响授权失效策略。 |
| Q5 | `Tc` 中保存工具 ID、权限点 code，还是二者都保存？ | 影响 IAM 颁发 `TR` 和 MCP 网关校验。 |
| Q6 | 静默命中历史授权时，IDaaS 返回 `Tc` 还是返回可换取 `Tc` 的一次性 code？ | 影响 Agent 网关接口编排。 |
| Q7 | 用户部分授权时，IDaaS 如何表达已授权、拒绝、待补充的工具列表？ | 影响业务 Agent 给用户解释。 |
| Q8 | 权限点停用、Agent 下架、用户冻结时，授权记录如何批量失效？ | 影响安全兜底。 |

## 9. 跨系统联动需求

虽然本文主要下发给 IDaaS，但以下能力需要跨系统同步确认：

- IAM 需要明确 `Tc + T1 -> TR` 的输入字段、校验规则和 `TR` 短期有效期策略。
- MCP 网关需要具备 `TR` 真实性校验、工具权限校验、策略中心调用能力。
- MCP 网关需要明确是否由自身将 `TR` 解析为必要的用户身份上下文，并携带给真实人机接口工具。
- IDaaS 需要支持 MCP 网关携带 `TR` 做令牌合法性校验，并在校验通过后提供 `TR` 转 Cookie / 用户身份上下文能力。
- Agent 网关需要明确卡片弹窗和 302 授权页两种模式下，与 IDaaS 的请求和回调协议。

## 10. 建议推进优先级

第一阶段先完成 P0 能力，交付时间为 2026-06-10：

- `agent_id` 维度授权隔离。
- 授权查询。
- 全量已授权静默返回。
- 部分未授权弹出授权确认。
- 用户部分授权。
- `Tc` 发放。
- 历史授权保存。
- 工具追加授权。
- 支持 MCP 网关携带 `TR` 做 IDaaS 令牌合法性校验。
- 支持 `TR` 转 Cookie / 用户身份上下文。

第二阶段补齐 P1 体验和治理能力，交付时间为 2026-06-20：

- 会话级隔离策略。
- 临时/长期授权选择。
- 跨会话授权同步。
- 授权撤销与审计页面。
- Agent 下架、权限点停用、用户冻结等批量失效。

第三阶段完成 P2 联调和体验增强，交付时间为 2026-06-25：

- 会话级隔离导致重复授权时的一键同步或授权复用体验。
- 与 Agent 网关、IAM、MCP 网关完成 Beta 端到端联调。
- 对授权查询、授权确认、`Tc` 发放、`TR` 合法性校验、`TR` 转 Cookie、工具调用放行链路完成闭环验证。
