## 1. IDaaS回调成功后，业务页面仍返回500

### 现象与影响

用户在IDaaS完成登录，浏览器已回调网关并收到`ticketST`；业务Agent后端交换票据时失败，页面返回500。外部token接口返回400，并提示`Client Authentication Method: client_secret_basic`。用户看到的页面错误和真实失败点不在同一个模块。

### 定位路径

1. 确认浏览器已完成IDaaS到网关、网关到业务Agent的302链路，票据已生成。
2. 追踪业务后端的`/gw/auth/ticket/exchange`调用，定位至`GatewayAuthService.exchangeLoginTicket`。
3. 沿调用栈进入`RealIdaasTokenClient.exchangeAuthorizationCode`及token HTTP请求，发现失败发生在userinfo之前。
4. 比较外部错误与客户端请求：旧实现将客户端凭据放在表单中，而目标接口要求Basic客户端认证。

### 根因与修复

根因是客户端认证方式与IDaaS实际要求不一致。提交`e878ecc`（2026-04-29）移除表单中的`client_id/client_secret`，改为使用`headers.setBasicAuth(clientId, clientSecret)`；表单保留`grant_type/code/redirect_uri`，同步修改测试断言。

### 复现与回归

历史故障复现方法：使用要求Basic认证的token端点，在测试客户端采用旧表单凭据方式，预期被拒绝；采用修复后的Basic请求则可通过协议检查。不得把模拟返回的成功当成真实IDaaS环境复验。

当前自动化依据是`RealIdaasTokenClientTest.shouldExchangeCodeWithFormUrlencodedRequest`，同时断言表单类型、Basic认证头和表单字段。本次53个测试中该用例通过；真实环境修复完成时间及服务端成功日志需要另附。

## 2. IAM业务Agent AI账号拼接错误

### 现象与影响

联调发现业务Agent的AI账号名按appId拼接，与IAM实际使用的`Agent_ + agentId`不一致，影响T1申请定位正确的委托账号。原始IAM错误码和失败日志未作为附件保存，本材料不补造具体响应。

### 定位路径

1. 区分网关自身AI账号、业务Agent的appId、业务Agent的agentId，核对它们在三段令牌流程中的用途。
2. 检查`RealIamAssumeAgentTokenClient`中`delegator_account_name`的构造来源。
3. 对照IAM约定，确认账号名应使用agentId，`delegator_appid`仍应使用appId。
4. 同步检查mock T1/TR生成逻辑与断言，避免本地模拟继续掩盖真实字段来源错误。

### 根因与修复

提交`acefde8`（2026-04-29）将业务AI账号名改为`Agent_ + agentId`，并同步调整mock令牌生成、测试和相关设计文档。

示意数据仅用于说明字段来源：

```json
{
  "delegator_account_name": "Agent_agt_business_001",
  "delegator_appid": "com.huawei.business.agent"
}
```

### 复现与回归

构造`agentId`与`appId`明显不同的Agent配置，检查发往assume接口的请求体；若账号名出现appId，即可稳定发现旧问题。

`RealIamAssumeAgentTokenClientTest.shouldAssumeBusinessAgentTokenWithGatewayToken`断言上述字段、正式路径、直接Authorization头，并检查请求体不额外携带`agent_id`。当前用例通过；`JwtTokenFactoryTest`验证mock令牌相关字段。尚需附IAM真实环境复验记录。

## 3. 真实TR结构变化导致鉴权上下文读取不一致

### 现象与影响

真实IAM的TR中，`consented_scopes`为权限点code字符串数组，用户信息位于`agency_user.user`的JSON字符串中，Agent ID位于顶层`aud`。按旧对象数组或旧用户字段读取，会导致解析失败或鉴权使用错误来源。此案例属于接口变化适配，不将协议约定变化直接计为历史代码缺陷。

### 定位路径

1. 对比真实TR反馈中的字段类型与本地mock生成、网关响应及Demo解析逻辑。
2. 明确运行时三个来源：权限点为`agency_user.consented_scopes`，用户为解析`agency_user.user`后的`uid`，Agent为`aud`。
3. 明确顶层`scope`仅作预留，不能在缺少实际授权范围时兜底。
4. 检查影响链路：Tc读取、mock TR生成、TR交换响应、Demo缓存、Mock/Real MCP客户端和测试。

### 修复范围

提交`68aef64`（2026-04-30）统一字符串数组，新增集中解析类`TrTokenParser`，同步生成器、DTO、调用逻辑、设计文档和回归测试。

```text
Agent ID   <- TR.aud
用户 ID    <- JSON.parse(TR.agency_user.user).uid
权限点集合 <- TR.agency_user.consented_scopes
```

### 复现与回归

使用不含真实凭据的合成载荷，故意让顶层`scope`与`consented_scopes`不同，断言只能读到后者；另构造旧对象数组并断言拒绝，构造请求Agent与`aud`不同并断言拒绝。

当前通过的测试包括`TrTokenParserTest.shouldReadAgentUserAndPermissionPointsFromRealIamPayloadShape`、`shouldRejectObjectConsentedScopes`以及`MockMcpGatewayClientTest.shouldRejectWhenTrAudienceDoesNotMatchRequestAgent`。这些验证载荷解析与业务规则，不验证真实IAM签名。
